The weather server

One TypeScript file that turns the US National Weather Service API into an MCP server. It shows almost every server-side feature of MCP: tools with typed output, resources you can subscribe to, an interactive widget, a URL elicitation and both transports.

1. A tool: get-forecast

A tool is a name, a description the model reads to decide when to call it, an input schema and a handler. The input schema (here written with zod) is checked before the handler runs, so a latitude of 200 never reaches your code.

server.registerTool(
  "get-forecast",
  {
    title: "Get Weather Forecast",
    description: "Get weather forecast for a location",
    inputSchema: z.object({
      latitude: z.number().min(-90).max(90).describe("Latitude of the location"),
      longitude: z.number().min(-180).max(180).describe("Longitude of the location"),
    }),
    outputSchema: forecastOutputSchema,
  },
  async ({ latitude, longitude }) => {
    // ...two NWS calls: /points/{lat},{lon}, then the forecast URL it returns
    return { content: [{ type: "text", text }], structuredContent: forecast };
  },
);

Two answers in one result

Every tool result returns the same answer twice. content is text for the model to read. structuredContent is typed data for the app, and it must match the tool's outputSchema. The client SDK checks that for you.

When something goes wrong, the handler throws. The SDK turns that into a result with isError: true, which the model sees and can recover from, for example by trying another location. That is different from a protocol error, such as calling a tool that doesn't exist.

2. An array result and a widget: get-alerts

get-alerts returns a list, so its outputSchema is a top-level array. Spec 2026-07-28 is the first version to allow that; for older clients the SDK wraps it as { "result": [...] } automatically.

It is also registered as an MCP App tool. Its _meta.ui.resourceUri points at an HTML resource, and hosts that support MCP Apps (such as Claude Desktop) show that page in a sandboxed frame next to the result. In the widget, picking another state calls get-alerts again through the host, then tells the model what the user is now looking at.

registerAppTool(server, "get-alerts", {
  title: "Get Weather Alerts",
  inputSchema: z.object({ state: z.string().length(2) }),
  outputSchema: alertsOutputSchema,          // z.array(z.object({ event, area, ... }))
  _meta: { ui: { resourceUri: ALERTS_VIEW_URI } },
}, async ({ state }) => { /* ... */ });

3. Resources and live updates

Tools are chosen by the model; resources are read by the app. A resource template like weather://alerts/{state} covers many URIs, and its list callback says which ones to show (by default FL, CA and NY).

Over HTTP, the server polls the watched states every 60 seconds. When a state's alerts change it sends notifications/resources/updated to clients that subscribed through subscriptions/listen. The rotating resource does the same on a timer, so you can test subscriptions without waiting for real weather.

cd mcp/weather-server-typescript
node build/index.js --http           # serves http://127.0.0.1:3333/mcp
node scripts/listen.mjs FL           # second terminal: prints each update

4. Asking the user: URL elicitation

A server can't keep a request open while it waits for the user, because the 2026-07-28 protocol is stateless. Instead it answers input_required with what it needs, and the client calls the tool again with the user's answer attached. Here the server asks the client to open a web page, which is how a real server would send someone to a login or payment page without the secret ever passing through the chat.

const answer = inputResponse(ctx.mcpReq.inputResponses, "login");
if (answer.kind === "missing") {
  return inputRequired({
    inputRequests: {
      login: inputRequired.elicitUrl({
        message: "Open the Facebook login page in your browser?",
        url: "https://www.facebook.com/login",
      }),
    },
  });
}
// second call: answer.action is "accept", "decline" or "cancel"

5. Two transports, one server

The same buildServer() runs over either transport. stdio is the default: the host starts the server as a child process and they exchange one JSON-RPC message per line. With --http it serves Streamable HTTP on 127.0.0.1:3333/mcp, bound to localhost with origin checks on.

if (process.argv.includes("--http")) {
  const handler = createMcpHandler((ctx) => buildServer(ctx.era === "modern"), { onerror });
  const app = createMcpHonoApp();
  app.all("/mcp", (c) => handler.fetch(c.req.raw));
  serve({ fetch: app.fetch, port, hostname: "127.0.0.1" });
} else {
  serveStdio(() => buildServer(), { onerror });
}

Over stdio, anything the server prints must go to stderr: stdout carries only MCP messages, so a stray console.log would break the connection. That is why every log line in this file uses console.error.
